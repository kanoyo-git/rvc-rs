# Скорость и ресурсы RVC на Rust

Замеры от 19 ноября 2026 года на Linux, Ryzen 5 5600 и GeForce RTX 5060 8 ГиБ. Эталон Python взят из коммита `81eed5e8f68b6bed1789f682fe78cdd324495afc`. Использовались Python 3.12.16, PyTorch 2.7.0 и LibTorch 2.7.0, для GPU с CUDA 12.8. Замеры выполнены на двух физических ядрах и с одинаковыми лимитами потоков. Для CPU-реалтайма также приведён прогон на шести физических ядрах. Rust собран с оптимизациями профиля `release`.

## Конвертация

RVC v2, 40 кГц, ContentVec и RMVPE. CUDA запускалась на явном устройстве `cuda:0` в FP16. По одному прогревочному и три замеренных запуска каждого CLI. Одиночный файл длится 0,9 с, пакет из трёх файлов длится 8,1 с. Время включает запуск процесса, чтение модели, конвертацию и запись WAV.

| Нагрузка | Время, с Python → Rust | CPU, с Python → Rust | RSS, МиБ Python → Rust | VRAM, МиБ Python → Rust |
| --- | ---: | ---: | ---: | ---: |
| CPU, один файл | 11,93 → 1,84 | 14,03 → 3,15 | 1 843 → 1 129 | — |
| CPU, пакет | 18,34 → 6,29 | 28,54 → 12,05 | 2 096 → 1 632 | — |
| CPU, один файл с retrieval 0,75 | 9,92 → 1,58 | 12,32 → 2,81 | 1 834 → 1 072 | — |
| CUDA, один файл | 10,51 → 3,49 | 10,61 → 3,74 | 2 805 → 2 566 | 1 222 → 726 |
| CUDA, пакет | 12,59 → 3,78 | 12,89 → 4,05 | 2 886 → 2 567 | 2 466 → 852 |

В полной Linux-сборке порядок библиотек исправлен так, чтобы матричные операции LibTorch выполняла его BLAS. Веса передаются на GPU сразу в выбранной точности. Вход, веса, настройки и геометрия выходных WAV совпадают. Для retrieval оба движка прочитали один созданный Rust индекс IVF10/Flat из 416 векторов. Генератор использует случайный шум, поэтому сэмплы двух независимых прогонов могут различаться.

Декодер Rust рассчитывает оставляемый фрагмент и контекст его свёрток. На CPU у RVC v2 медиана трёх прогретых конвертаций снизилась с 2,00 до 1,00 с, а пиковый RSS процесса — с 1 265 до 1 079 МиБ. При одинаковом seed итоговые сэмплы совпали. На v1 и v2 без F0 максимальная разность составила один шаг PCM16.

Отдельный CPU-прогон того же WAV с синтетическим RVC v1 дал 9,87 → 1,48 с и 1 753 → 1 165 МиБ RSS.

Свёртки в CPU-инференсе RVC используют раскладку channels-last на LibTorch с oneDNN и двумя или более потоками. В парном замере на v2 медиана прогретой конвертации снизилась с 0,98 до 0,82 с. С одинаковым seed максимальная разница для v2, синтетического v1 и синтетического v2 без F0 составила один шаг PCM16.

Сборка с ONNX Runtime CPU использовала те же файлы весов. Сквозное сравнение с одним seed дало максимальную разницу в один шаг PCM16 для тех же трёх генераторов. До смены раскладки CPU отдельный прогон v2 с тремя прогретыми конвертациями дал медиану 1,12 с для LibTorch и 1,00 с для ONNX. Пиковый RSS за весь прогон составил 1 240 и 1 324 МиБ соответственно.

## Реалтайм

Модель обрабатывает блоки по 250 мс, 2,5 с истории, без retrieval. CUDA-сборка использует CUDA-графы с общим пулом. После прогрева измерено 60 блоков на CUDA и на шести CPU-ядрах и 20 блоков на двух CPU-ядрах.

| Нагрузка | p50, мс Python → Rust | p95, мс Python → Rust | Опоздавшие блоки Python → Rust | CPU, с Python → Rust | RSS, МиБ Python → Rust | VRAM, МиБ Python → Rust |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| CPU, два ядра | 462,71 → 387,07 | 471,66 → 405,96 | 20/20 → 20/20 | 31,28 → 20,38 | 1 604 → 1 125 | — |
| CPU, шесть ядер | 278,26 → 188,88 | 300,93 → 194,45 | 60/60 → 0/60 | 118,85 → 75,60 | 1 608 → 1 078 | — |
| CUDA | 14,39 → 13,19 | 18,46 → 16,28 | 0/60 → 0/60 | 11,49 → 4,62 | 2 689 → 2 535 | 878 → 742 |

В другом прогоне CUDA p95 составил 14,74 мс у Python и 15,18 мс у Rust. В обоих прогонах все блоки уложились в 250 мс.

При загрузке одних и тех же нативных библиотек Torch финальная сборка и Python уложились в срок на всех 60 блоках. Python → Rust дал p50 14,01 → 13,44 мс, p95 14,71 → 15,75 мс, CPU 11,03 → 4,52 с, RSS 2 671 → 1 948 МиБ и VRAM 878 → 742 МиБ. В предыдущем парном прогоне с теми же библиотеками p95 составил 19,90 → 16,19 мс.

Сквозной CUDA-прогон через изолированный PipeWire при 48 кГц и блоках по 100 мс обработал 59 блоков за 6 с. Счётчики потерь входных кадров, выходных блоков и сбоев устройств остались нулевыми. Время обработки модели из таблицы измерялось отдельно от задержки аудиоустройств.

В контрольном сквозном прогоне одновременная смена формант и первое включение FCPE дали 13 440 потерянных входных кадров и один выходной блок. После фонового прогрева FCPE и исправления очереди воспроизведения четыре финальных прогона с переключениями RMVPE, PM и FCPE обработали суммарно 232 блока. Потерь входных кадров и выходных блоков не зарегистрировано. Два прогона использовали CUDA-графы, два выполнялись с `RVC_CUDA_GRAPH=0`. Активация FCPE заняла 0,41–0,70 с, в этот период работал прежний метод F0.

Финальную CUDA-сборку с нативным набором библиотек Torch проверили в отдельной сессии D-Bus с двумя виртуальными устройствами PipeWire и непрерывным контрольным сигналом. Все 57 обработанных блоков прошли без потерь в очередях и сбоев устройства. Первое переключение на FCPE заняло 447 мс. За это время выход дополнился 64 кадрами тишины, около 1,3 мс при 48 кГц.

Приложение и VST используют оконный sinc-фильтр Hann с коэффициентами, рассчитанными при запуске потока. На одинаковых блоках входного PCM и синтеза максимальная разница с фильтром Torchaudio составила 2,38 × 10⁻⁷. В изолированном замере обработка блока сократилась с 12,99–16,32 мс до 0,079–0,136 мс. Время расчёта коэффициентов и вызов нейросети измерялись отдельно. В двух сквозных CPU-прогонах PipeWire при 44,1 и 48 кГц обработано по 13 блоков по 250 мс без потерь входа и выхода.

### Полная обработка PCM на CPU

В трёх парных прогонах оригинальный VST-воркер Python и потоковый контекст Rust обрабатывали моно PCM 48 кГц. Оба использовали одни и те же библиотеки Torch 2.7.0, голосовую модель 40 кГц, RMVPE, блоки 250 мс, кроссфейд 50 мс, контекст 2,5 с и выравнивание RMS. Процессы запускались поочерёдно на двух физических ядрах. В каждом запуске первые 12 блоков прогревали модель, ещё 20 измерялись. Таймер охватывал ресемплинг, модель, выравнивание RMS и склейку блоков. Расход CPU и пиковый RSS измерялись за весь запуск, включая загрузку и прогрев.

| p50, мс Python → Rust | p95, мс Python → Rust | Опоздавшие блоки Python → Rust | Медиана CPU, с Python → Rust | Медиана пикового RSS, МиБ Python → Rust |
| ---: | ---: | ---: | ---: | ---: |
| 620,95 → 526,52 | 676,70 → 548,17 | 60/60 → 60/60 | 49,16 → 34,70 | 1 989 → 1 117 |

Во время замера фоновая нагрузка занимала около трети доступного процессорного времени выбранных ядер с учётом SMT. Каждый запуск вернул 240 000 отсчётов с конечными значениями. Медиана RMS составила 0,08315 у Python и 0,08313 у Rust. В этом замере использовалось правило истории исходного GUI, которое также обновляет предыдущие 10 мс.

Итоговый VST-прогон повторили на шести физических ядрах с теми же весами, PCM и настройками. Плагин обновляет текущий блок истории на 16 кГц, как исходный VST-воркер. Оба ресемплера получают предыдущие 20 мс входа для расчёта фильтра.

## Подготовка, обучение и разделение

Медианы трёх прогонов на CPU. Обучение выполняло одну эпоху без F0, v2 32 кГц, пакет 1, четыре обучающих клипа и два фрагмента тишины. Замер включает сохранение генератора, дискриминатора и экспорт компактной модели. HTDemucs4 выделял четыре дорожки из 4,8 с стерео на одинаковых каталожных весах.

| Этап | Время, с Python → Rust | CPU, с Python → Rust | RSS, МиБ Python → Rust |
| --- | ---: | ---: | ---: |
| Подготовка WAV | 2,28 → 0,52 | 3,50 → 0,63 | 219 → 119 |
| Извлечение HuBERT | 6,85 → 1,28 | 7,76 → 2,13 | 932 → 581 |
| Индекс FAISS | 1,48 → 0,26 | 1,63 → 0,27 | 151 → 118 |

После добавления восстановления чекпойнтов тот же сценарий обучения повторили на другой паре физических ядер. Медианы трёх парных прогонов Python → Rust составили 45,54 → 14,34 с, CPU 39,01 → 24,54 с и RSS 4 008 → 2 151 МиБ. Все запуски записали оба чекпойнта и экспортировали модель.

На RTX 5060 обе версии выполнили шесть итераций обучения в FP16 AMP, сохранили чекпойнты генератора и дискриминатора и экспортировали компактную модель. Признаки HuBERT проверены отдельно на тех же четырёх клипах. Тип данных и формы тензоров совпали, относительная RMS-разница составила 0,143%. В финальном повторном сравнении оба процесса загружали одни и те же нативные библиотеки из пакета PyTorch 2.7.0+cu128. Rust открывал их напрямую, без интерпретатора Python. Для каждого этапа приведена медиана трёх парных прогонов на тех же входах. Каждый запуск обучения сохранил оба чекпойнта и экспортировал модель.

Изолированный C++ процесс с отдельным архивом LibTorch отобразил 773 МиБ анонимной памяти ещё до создания тензоров. С нативными библиотеками из пакета PyTorch тот же процесс отобразил 179 МиБ. Сборка Rust также загрузила эти библиотеки из отдельного дерева без Python-модулей и выполнила CUDA-конвертацию. [Настройка библиотек](../README.md#сборка).

Чтение весов с последовательной передачей тензоров на GPU снизило медианный пик RSS Rust с 2 124 до 1 975 МиБ. Обе дорожки до и после изменения совпали до сэмпла. Максимальная разница с Python на контрольном сигнале составила 5,9 × 10⁻⁵. В отдельном тесте внимания на RTX 5060 результат cuDNN, FlashAttention и `efficient` в FP16 отличался от `math` максимум на 4,9 × 10⁻⁴.

С одинаковыми бинарными библиотеками Torch cuDNN не смог построить план для отдельных слоёв. На той же настройке `cuda_attention_backend=cudnn` обе версии обработали файл с автоматическим выбором ядра для этих слоёв. Медиана трёх парных прогонов Python → Rust составила 6,93 → 2,87 с, CPU 6,86 → 3,01 с, RSS 1 924 → 1 403 МиБ и VRAM 930 → 920 МиБ. Максимальная разница между сэмплами дорожек составила 6,4 × 10⁻⁵, относительная RMS-разница — до 0,13%.

На синтетических моно и стерео примерах Mel-Band-RoFormer и BS-RoFormer максимальная разница между выходами MLX CPU и LibTorch CPU составила 2,4 × 10⁻⁶ в FP32 и 5,6 × 10⁻⁵ в FP16. Проверка охватывала преобразования спектра, маски и WAV после сборки окон.

При отдельной проверке переноса внимания, слоя внимания и трансформера RoFormer в MLX на CPU максимальная разница с LibTorch составила 7,2 × 10⁻⁷ в FP32 и 2,9 × 10⁻³ в FP16. Ниже заданного порога длины проверка подтвердила совпадение с обычным вычислением LibTorch.

На четырёх синтетических конфигурациях MDX23C максимальная разница между выходами MLX CPU и LibTorch CPU составила 1,0 × 10⁻⁷ в FP32 и 4,9 × 10⁻⁴ в FP16. Прогон охватывал четыре варианта нормализации, GELU, ReLU и ELU, стерео с одной и несколькими дорожками и обработку трёх окон за пакет.

На этих же конфигурациях MDX23C разница между ONNX CPU и LibTorch CPU составила до 1,4 × 10⁻⁷. Отдельный пакетный прогон графа через DirectML под Wine зарегистрировал 217 выполнений узлов на DirectML и 45 на CPU.

В SCNet сравнение MLX CPU с LibTorch CPU на моно и стерео включало прямое и обратное STFT, двунаправленные LSTM, преобразования между слоями и сборку трёх окон за пакет. Максимальная разница составила 5,0 × 10⁻⁸ в FP32 и 9,9 × 10⁻⁵ в FP16.

Для Apollo максимальная разница между MLX CPU и LibTorch CPU составила 8,0 × 10⁻⁷ в FP32 и 1,2 × 10⁻⁴ в FP16. Для Bandit и Bandit v2 на восьми сквозных сценариях она составила 4,5 × 10⁻⁸ и 7,7 × 10⁻⁵. Проверены стерео, пакет из трёх окон и варианты LSTM, GRU и RNN.

Для UVR VR в восьми сценариях максимальная разница с LibTorch CPU составила 1,2 × 10⁻⁷ у ONNX CPU и MLX FP32, 9,4 × 10⁻⁵ у MLX FP16. Проверены штатный чекпойнт, две архитектуры VR, TTA и постобработка. Для современного графа с LSTM под Wine зарегистрировано 240 выполнений узлов на DirectML.

Для штатных HTDemucs4 и HTDemucs4_6stems максимальная разница MLX FP32 составила 8,6 × 10⁻⁶. Проверены полное окно в 485 100 сэмплов и пакет из трёх окон с дополнением до длины обучающего сегмента. Сокращённое окно из 3 072 сэмплов на HTDemucs4 дало 9,3 × 10⁻⁴ в FP16.

Для BS-RoFormer, Mel-Band-RoFormer и HyperACE с обычными масками максимальная разница ONNX CPU составила 3,0 × 10⁻⁸. Для HyperACE в режимах `full` и `segm_only` на том же контрольном стереосигнале разница составила до 2,4 × 10⁻⁴ у ONNX CPU и 5,9 × 10⁻⁴ у MLX FP32. Относительная RMS-ошибка MLX FP32 не превысила 0,27%. Под Wine граф BS-RoFormer зарегистрировал 405 выполнений узлов на DirectML и 13 на CPU, граф HyperACE `full` зарегистрировал 1 478 выполнений на DirectML и 60 на CPU.

В сквозных прогонах ONNX CPU максимальная разница с LibTorch составила 6,0 × 10⁻⁸ для SCNet и Apollo, 3,0 × 10⁻⁸ для Bandit и Bandit v2 и 3,2 × 10⁻⁶ для HTDemucs с полным окном. У старых Demucs, HDemucs и ConvTasNet разница была до 1,5 × 10⁻⁶ в десяти сценариях, включая штатные веса, двунаправленный LSTM и каузальный ConvTasNet. Под Wine проверено выполнение этих графов на DirectML. На контрольных входах максимальное расхождение DirectML и ONNX CPU в FP32 не превысило 1,3 × 10⁻⁵.

В ONNX-графах BS-RoFormer и Mel-Band-RoFormer FP16 уменьшил файлы внешних тензоров вдвое. Максимальная разница WAV между FP16 и FP32 в прогонах ONNX CPU составила 5,2 × 10⁻⁴, включая фрагменты тишины. Графы FP16 также выполнены через DirectML под Wine.

CPU — сумма пользовательского и системного времени. RSS берётся из Linux `wait4` и отражает пиковый RSS отдельного процесса, включая дождённых детей по правилам `getrusage`. Суммарная одновременная память дерева процессов отдельно не измерялась. VRAM опрашивалась по PID с интервалом 200 мс, поэтому кратковременные пики могли остаться между выборками.
